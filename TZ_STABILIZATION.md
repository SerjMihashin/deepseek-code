# TZ_STABILIZATION — DeepSeek Code

## Цель

Стабилизировать опубликованный npm-пакет `@serjm/deepseek-code` и затем аккуратно продолжить UI/UX overhaul.

Главный принцип:

> Агент не имеет права говорить “сделал”, если нет подтверждения через tool call, git diff/status или тесты.

## P0 — Критические баги доверия и безопасности

## P0.0 — Token Accounting Audit

Проблема:
простые задачи показывают огромный расход токенов, например 279k+ tokens на анализ нескольких файлов. Непонятно, это реальный расход, cached input, сумма по запросам или ошибка подсчёта.

Требования:
- Разделить total input, cached input, cache miss/new input, output, reasoning.
- Показывать количество API calls.
- Показывать max single request context.
- Проверить, не суммируются ли cumulative stream usage как incremental.
- Для каждого API call хранить raw usage.
- Execution Summary должен объяснять, что именно считается.
- Если usage недоступен, писать unknown, а не придумывать.

Acceptance:
- простая задача с 1 read_file показывает понятный breakdown;
- cached tokens не выглядят как новый расход;
- stream usage не удваивается;
- summary не пугает одной общей цифрой без пояснений.

## P0.0 — Input Integrity / Prompt Delivery

Проблема:
при вставке большого промта UI визуально обрезает/ломает текст. Непонятно, отправляется ли в модель полный текст или только видимая часть.

Требования:
- Перед отправкой вычислять длину prompt в chars.
- Считать количество строк.
- Для debug/dev режима показывать hash полного prompt.
- Большой paste отображать компактно, но хранить полный текст.
- Enter должен отправлять полный buffer.
- UI preview не должен влиять на реальное содержимое prompt.
- Если prompt был обрезан лимитом, явно предупреждать пользователя.

Acceptance:
- вставка большого текста показывает корректные chars/lines;
- отправляется полный текст;
- короткий input работает как раньше;
- slash-команды не ломаются;
- пользователь видит, если prompt слишком большой.

### P0.1 Change Verification / Execution Ledger

Проблема:
агент может отчитаться, что изменил файлы, хотя на диске изменений нет.

Требования:
- `write_file` и `edit` должны возвращать `changed`, `verified`, `changedFiles`.
- `edit` с 0 замен не считается успешным.
- После правок агент обязан сверять состояние через git status/diff или внутренний ledger.
- Финальный отчёт `changed files` строится только из фактических изменений.
- Если diff пустой — писать: “Изменений нет”.
- Добавить `/last-run` или аналог для просмотра последнего ledger.

Acceptance:
- агент создаёт тестовый файл → отчёт показывает файл;
- агент ничего не меняет → отчёт пишет “изменений нет”;
- при failed edit не пишет “изменил”.

### P0.2 Запрет фальшивых отчётов

Проблема:
агент пишет “проверил”, “посмотрел лог”, “изменил”, хотя tool call не выполнялся.

Требования:
- Ответы делить на Verified / Failed / Skipped / Assumption.
- Нельзя писать “проверено”, если не было команды или tool call.
- Локальные команды и summary должны показывать реальные tool results.
- Если Tool uses = 0, нельзя заявлять выполненные действия.

Acceptance:
- вопрос “что ты изменил?” при пустом diff → “ничего не изменено”;
- отчёт не содержит выдуманных файлов;
- summary не противоречит tool calls.

---

### P0.3 Ограничение расхода токенов

Проблема:
простые UI-задачи сжигали сотни тысяч и миллионы токенов.

Требования:
- Для маленьких задач максимум 10–15 tool calls.
- Не читать весь проект без необходимости.
- Не читать большие HTML/DOM в контекст.
- Если задача разрастается — остановиться и попросить сузить scope.
- В отчёте показывать tool calls и token usage.

Acceptance:
- задача `/help` не должна читать десятки файлов;
- browser smoke-test не должен тянуть полный HTML больших сайтов;
- при превышении лимита есть partial report.
